Fix the two review findings from `06-REVIEW.md` that are (a) real correctness/honesty defects and (b) fixable and testable purely in shared/`commonMain` Kotlin without any hardware or Android BLE stack: CR-01 (Critical: RaceBox frame parser silently drops a legitimate frame when its 2-byte sync sequence is split across two `accept()` calls) and WR-03/WR-04 (Warning: unbounded NMEA stream buffer growth, and NMEA horizontal accuracy populated directly from unitless HDOP). **Explicit scope decision (per this gap-closure's instructions, documented rather than silently applied):**

- **In scope, fixed here:** CR-01, WR-03, WR-04. All three are pure-Kotlin, hardware-independent, already covered by an existing host-test suite (`RaceBoxFrameParserTest`, `Nmea0183ParserTest`), and each review finding already ships a concrete fix in `06-REVIEW.md`. Fixing them satisfies the Nyquist rule (automated verification exists/is added) without requiring any new test infrastructure.
- **Deferred, NOT fixed here (Task 3 records this in `06-HARDWARE-RISK.md`):** WR-01 (`BluetoothGatt` leak on reconnect), WR-02 (`discoverServices()` swallows failures), and WR-05 (zero test coverage of `AndroidExternalGnssBleClient`) all live in `androidApp/src/main/kotlin/com/huanfuli/lapsight/ExternalGnssBleClient.kt`, which today has **zero automated test coverage of any kind** (confirmed by `06-REVIEW.md` WR-05 itself). Fixing WR-01/WR-02 without a way to verify the fix would violate the Nyquist rule (every task must have an automated `<verify>`); building that verification requires extracting a testable seam around `BluetoothAdapter`/`BluetoothGatt` (a nontrivial refactor, not a two-line fix) or real hardware, both already tracked as accepted/deferred hardware-path risk under D-02. This is a scope/verifiability decision, not a difficulty judgment: the fix code is simple, but there is no way to prove it works without either the refactor or a real receiver. IN-02 is a manifest-comment accuracy issue with zero behavior impact -- deferred as trivial cleanup, not worth its own task in a gap-closure pass scoped to the connection-status UI gap and adjacent hardware-independent parser bugs.

    In `RaceBoxFrameParser.accept()`, replace the `syncIndex &lt; 0 ->` branch. Instead of unconditionally discarding the whole `streamBuffer` (current behavior: `streamBuffer = ByteArray(0)`), compute `keepTrailingByte = streamBuffer.isNotEmpty() &amp;&amp; streamBuffer.last().toUnsignedInt() == SYNC_1` and `garbageLength = if (keepTrailingByte) streamBuffer.size - 1 else streamBuffer.size`. Emit a `Rejected(reason = MissingSync, rawFrame = streamBuffer.copyOfRange(0, garbageLength))` only when `garbageLength > 0` (preserves the existing "no result on truly empty buffer" behavior). Set `streamBuffer` to `streamBuffer.copyOfRange(garbageLength, streamBuffer.size)` when `keepTrailingByte` is true (i.e. the single trailing `SYNC_1` byte), or `ByteArray(0)` otherwise. Keep the `break` at the end of this branch unchanged. `SYNC_1` is directly accessible from inside `accept()` without qualification (companion member of the enclosing class).

    Add a new test `fragmentedInputSplitExactlyAtSyncBoundaryStillDecodes` in `RaceBoxFrameParserTest.kt`, modeled directly on the existing `fragmentedInputMatchesWholeFrameInput` test: build `first`/`second` via `RaceBoxFrameBuilder.liveFix(...)` with two different `iTowMillis`/`latitudeDegrees` values (reuse the same values as the existing test for consistency), concatenate into `burst`, compute `whole = RaceBoxFrameParser().accept(burst).snapshots()`, then feed a fresh parser `burst.copyOfRange(0, 1)` (exactly the lone `0xB5` byte) followed by `burst.copyOfRange(1, burst.size)` (everything else, starting with `0x62`), collect both results into one list, and assert the collected snapshots equal `whole`.
  </action>
