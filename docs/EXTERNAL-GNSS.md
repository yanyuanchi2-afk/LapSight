# LapSight — External GNSS Support (Phase 6)

**Status:** Protocol-complete, hardware-unvalidated
**Covers:** EXT-01, EXT-02, EXT-03
**Last updated:** 2026-07-07 (Phase 6 Plan 04 closeout)

---

## 1. What "protocol-complete, hardware-unvalidated" means

Phase 6 was built as a protocol compatibility preview because the product
owner chose not to purchase a RaceBox or other external GNSS receiver for
this phase (see `.planning/phases/06-external-gnss-and-sensor-ingestion/06-CONTEXT.md`,
decision D-02). Concretely, that means:

- The NMEA 0183 and RaceBox protocol parsers, the shared `LocationSampleProvider`
  wiring, the Android BLE connection shell, and the Settings source picker are
  all implemented and covered by deterministic automated tests.
- Every test in this phase runs against **replay fixtures and synthetic,
  clean-room-generated bytes** — public NMEA logs, generated NMEA sentences, and
  a synthetic RaceBox frame builder authored in this repository. No RaceBox
  Mini/Mini S/Micro, no third-party NMEA receiver, and no real BLE radio has
  been used to produce or validate any of this data.
- Nothing in this document, the Settings UI, or the code claims that a real
  receiver has been connected, that BLE pairing/reconnect behaves as coded on
  real hardware, or that any accuracy/precision improvement over phone GPS has
  been observed. See `.planning/phases/06-external-gnss-and-sensor-ingestion/06-HARDWARE-RISK.md`
  for the explicit list of unvalidated risks and what future validation would
  need to check.

If you own a supported receiver and try External GNSS in LapSight, you are the
first real-hardware validation this feature has had. Feedback is genuinely
useful — see [Section 5](#5-if-a-real-receiver-fails-what-to-send-us).

## 2. Supported protocols

### 2.1 NMEA 0183 (default, lowest risk)

- Text-based, checksum-protected sentences over any byte-oriented transport
  (BLE UART-style notify characteristic, Bluetooth SPP, USB serial, TCP).
- Parsed sentences: `RMC` (time, fix validity, lat/lon, speed, course), `GGA`
  and `GNS` (fix quality, altitude, satellite count, HDOP), `VTG` (course/speed
  fallback). `GSA`, `GST`, and `ZDA` are recognized and intentionally ignored
  (diagnostic-only, not needed for a `LocationSample`).
- Malformed sentences, checksum mismatches, no-fix status, and fragmented byte
  reads are handled as typed parser outcomes, never a crash.
- This is the protocol Android's `ExternalGnssLocationProvider` defaults to,
  because it needs no vendor-specific GATT UUIDs beyond the widely used Nordic
  UART Service convention.

### 2.2 RaceBox protocol family (preview)

- Binary, UBX-like framing (sync bytes, message class/id, length, payload,
  two-byte checksum) targeting the RaceBox Mini, Mini S, and Micro live-data
  protocol, based on RaceBox's public protocol documentation page and product
  spec pages (see `06-RESEARCH.md` for sources). RaceBox Mini and Mini S share
  the same real-time GNSS class (25 Hz, multi-constellation); Micro additionally
  supports NMEA over BLE.
- Live GNSS fix frames decode into the same normalized fix model as NMEA:
  time, lat/lon, altitude, horizontal/vertical accuracy, speed, heading, speed
  and heading accuracy, satellite count, and a dual-frequency flag.
- A separate "basic telemetry" frame type carries optional acceleration, gyro,
  and vehicle-speed fields when a receiver's firmware exposes them. See
  [Section 3](#3-telemetry-vs-lap-timing-the-ext-03-boundary) for how LapSight
  treats this data.
- **Implementation provenance:** the parser was written clean-room against
  publicly described field semantics and this repository's own synthetic frame
  builder/tests. No GPL or unlicensed third-party RaceBox client code was
  copied into LapSight (D-07). RaceBox's exact BLE service/characteristic UUIDs
  are only published on request, so `AndroidExternalGnssBleClient` defaults to
  the common Nordic UART Service UUIDs and exposes constructor overrides for
  when a confirmed receiver's documentation is available.
- Not yet exposed as a Settings protocol choice — `ExternalGnssLocationProvider`
  already supports it via a constructor parameter, but Android Settings
  currently only offers the NMEA 0183 path end-to-end. Wiring a protocol picker
  is tracked as later Phase 6 follow-up work, not part of this closeout.

### 2.3 How protocol support was tested

All Phase 6 verification is replay-based (D-06):

- Deterministic host tests decode public/generated NMEA sentences and
  synthetic RaceBox frames covering valid fixes, no-fix/acquiring status, stale
  or malformed timestamps, checksum failures, malformed/truncated frames,
  fragmented byte reads, high-rate bursts, and reconnect gaps.
- `ExternalGnssTimingPipelineTest` (Phase 6 Plan 04) feeds decoded NMEA and
  RaceBox samples through the exact same `SessionController` timing pipeline
  used by phone GPS, over the same fixture geometry already used by the lap
  engine/session/ghost test suites, and asserts matching lap counts and lap
  timing, live-delta/ghost availability transitions, and distinct
  `ExternalGnss` session provenance versus `PhoneGps`/`Simulated`.
- Android-side connection state machine and byte-queueing logic
  (`ExternalGnssLocationProvider`) are exercised with a fake byte-stream test
  double — no BLE hardware or Android instrumentation required.

This proves that once bytes arrive from a receiver, LapSight decodes, labels,
records, and times them correctly. It cannot prove how a real receiver's BLE
service actually behaves, what its firmware quirks are, or how antenna
placement affects field accuracy.

## 3. Telemetry vs. lap timing (the EXT-03 boundary)

Phase 6 scopes EXT-03 narrowly, matching decision D-09 in `06-CONTEXT.md`:

- If a supported protocol exposes basic acceleration, gyro, or vehicle-speed
  fields (currently: RaceBox basic telemetry frames), LapSight may parse them
  as optional `ExternalGnssTelemetryMetadata` and surface them as a side
  channel (Android's `ExternalGnssLocationProvider` exposes a telemetry
  `StateFlow` separate from location samples).
- Telemetry frames **never** produce a `LocationSample` and never enter
  `nextSample()`/`drainPending()`. Lap timing, sector detection, and ghost
  delta remain driven exclusively by normalized GPS-derived location samples,
  exactly as they are for phone GPS and simulated replay. This is asserted
  directly by `ExternalGnssTimingPipelineTest`'s telemetry-interleaved-frame
  scenario.
- Phase 6 does **not** implement IMU sensor fusion, a vehicle-CAN integration,
  or any timing feature that depends on telemetry data. Absent telemetry (for
  example, every NMEA-only receiver, since NMEA 0183 has no telemetry channel)
  is handled cleanly — the corresponding field simply decodes as `null`, not an
  error or placeholder.
- Do not expect telemetry values (G-force, gyro, vehicle speed) anywhere in
  the current Drive dash or Review UI. They exist in the data model as
  protocol-driven optional metadata for future analysis features, not as a
  shipped user-facing capability in this phase.

## 4. What remains unvalidated without hardware

See `.planning/phases/06-external-gnss-and-sensor-ingestion/06-HARDWARE-RISK.md`
for the full risk register. In short: real BLE GATT service/characteristic
behavior, connection/reconnect timing on real firmware, antenna placement and
field accuracy, RaceBox model-specific differences (Mini vs. Mini S vs.
Micro), and any timing-precision claim relative to phone GPS are all
explicitly open until a real receiver or user field evidence exists.

## 5. If a real receiver fails, what to send us

If you try External GNSS with a real RaceBox or NMEA receiver and it does not
work as expected, the most useful report includes:

1. **Receiver model and firmware version** (e.g., "RaceBox Mini S, firmware
   X.Y.Z" or "generic NMEA 0183 BLE dongle, model ___").
2. **Phone model and Android version.**
3. **What you selected in Settings** (External GNSS source) and what happened
   — did the connection state show Scanning/Connecting/Connected/Failed, did
   it never leave Disconnected, did it connect then drop?
4. **Connection logs**, if you can capture Android `adb logcat` output around
   the time of the attempt (the BLE client logs scan/connect/notify
   transitions).
5. **An exported session or raw replay log** from LapSight for the attempt,
   if any samples were received at all — Review → the session or raw capture
   → export. This is the same JSON payload format used by `SessionReplayDecoder`
   internally, so it can be replayed exactly to reproduce what LapSight saw.

Without at least the receiver model + connection logs, it is very hard to
tell whether an issue is a protocol mismatch (e.g., different BLE UUIDs, a
different binary layout than modeled here) versus something else entirely.
